# DOP3010 UI element index - the operator's screenshot crops

**What this is.** An indexed, committed-ready record of the hand-cut PNG crops of the live user
interface of the ultrasound scanner application, taken while working the acquisition campaign. The
crops are the only oracle for the application's own button and field captions: the control tree
carries no text for the button classes, so a caption exists on the screen or not at all.

**Who captured it, and when.** The human operator, by hand, on **2026-09-18**, between 16:27 and
16:54 as the file mtimes run; values on screen are the operator's own working values, not patient
data, and nothing in the set is confidential.

**Application and mode.** `UDOP DOP3010.43` - the real instrument in **real-experiment mode** (not
the simulation build `UDOP Simul`), channel 1 routed throughout, the recording strip in view
`ready`. No crop contains the title bar, so the mode is carried by the plan and by this sentence
rather than by the pixels; see `Surfaces the plan names with no crop`.

**The set is PARTIAL.** This is an incomplete pass over the interface, captured in one session, and
it is expected to grow. It is not a screen-by-screen walkthrough: it is a set of regions the
operator chose, so a surface absent here is absent from the *set*, not from the application. Every
gap found is named in the two sections below.

**The `blocking` column** is the *only* field in this index that cannot be read from the pixels:
whether a cursor was captured by an overlay is not a property a crop can show. It comes from the
operator's own naming convention - a `-blocking` suffix means blocking - and where a filename carries
no suffix the cell says so (`no (from the naming convention)`) so the claim's source is visible.
Two overlay filenames carry no suffix although the operator's list calls them blocking; they are
called out in the cells and in `Cross-checks and findings`. Non-overlay crops (the bar, the column,
the strip, the dropdowns) are marked `n/a (not an overlay)`: the question does not arise for a
surface that is not an overlay at all.

**How the images were read.** Every one of the 30 files was opened and described from the pixels;
every numeric cell was then re-read from a x5-x6 nearest-neighbour magnification, and the cells that
disagreed between passes were settled by printing the glyph bitmaps and comparing them with the same
frame's own known digits. Three readings were corrected this way (see `Cross-checks and findings`).
No value in the table is inferred from the filename.

**Pixel dimensions** are recorded beside each filename. Total: 30 crops, 12 MENU, 15 OVERLAY, 1 SIDEBAR, 1 BAR, 1 STRIP.
The `WINDOW` family is defined but empty: no crop in the set falls outside the five families above.

`OVERLAY` (overlays and dialogs), `SIDEBAR` (the left parameter column), `BAR` (the bottom/status
strip), `STRIP` (the recording strip), `WINDOW` (anything else). Numbering runs the menu bar left to

the operator's own filename unchanged - that name is the stable key this index is built on.

## Known gaps

Two surfaces the operator did not screenshot, named verbatim as the operator reported them. Both are
surfaces on which the application **replaces the whole window with new contents** - a mode change, not
a panel - so neither is a region that a later crop can be added to: each needs the whole screen
recaptured while that surface is up.

1. **`Measure US field`** - the surface behind `Tools > Measure US field` (the menu entry is cropped
   as UI-MENU-09, the surface it opens is not). The window's contents are replaced wholesale, so
   there is nothing in this set that shows any field of it: not its controls, not its readouts, not
   its own captions. **For the index this means the surface is wholly uncovered** - no row in the
   table above describes it, and no field named in the plan (`Sampling volume`, the gate geometry,
   the sound-speed readout) can be cross-checked against a `Measure US field` screen. It also means
   the corpus has no evidence of what that screen would let a run read: every `Measure US field` claim
   rests on documentation until a capture exists.
2. **`Compare profiles`** - the surface behind `File > Compare profiles` (the entry is cropped as
   UI-MENU-02, the surface is not), with the same whole-window replacement. **For the index this
   means a second wholly uncovered surface**, and one that matters for a different reason: this is
   the screen on which two stored profiles are compared, so a crop of it would be the only direct
   evidence of how the application *presents* two recordings - and this index holds none.

Both gaps are total: the entry is cropped, the surface is not, so the index covers the gesture and
not the destination. Neither is a partial crop that could be extended; each needs the operator to
return to the surface and capture it (whole screen, since the window contents are replaced).

A third gap of the same kind was found while cross-checking, not reported by the operator: the
`Search artefacts` surface (`Tools > Search artefacts`, UI-MENU-09) is not cropped either, and the
file whose name suggests it (`overlay-search-artifacts.png`, UI-OVERLAY-15) shows a `Sweep PRF`
overlay instead.

## Cross-checks and findings

Each finding names the crop it rests on. The known facts supplied to this pass were treated as
independent measurements, so agreement is recorded as well as disagreement - a crop that agrees is a
second witness, and the traps are worth writing down because they reproduce.

1. **`PRF [us]` = `600` - confirmed, and the trap is real** (`UI-SIDEBAR-01`) - The crop confirms the known fact: the second value box reads `600`. The known `500`/`600` trap reproduced twice in this very pass - a read of the crop at its own size returned `500`, and only a x6 nearest-neighbour magnification (plus a glyph-level pixel comparison against the `5` of the same frame's `50`) returned `600`. Matches §22.2 row 2 and §23.3.
2. **`Resolution [mm]` = `1.850` - confirmed** (`UI-SIDEBAR-01`) - The fourth value box reads `1.850`, as the known facts state; matches §22.2 row 4 and §23.3.
3. **The `Tgc [dB]` row is NOT painted in the cropped column** (`UI-SIDEBAR-01`) - The plan reads ten painted rows on the instrument's column, with `Tgc [dB]` = `20` (§22.2 row 8, §22.3). This crop paints NINE rows - `US Frequency`, `PRF`, `Nb of gates`, `Resolution`, `Velocity scale factor`, `Emissions/profile`, `Doppler angle`, `Sensitivity`, `Emitting power` - and no `Tgc [dB]` row. The crop also contains the two rows that follow it in the plan's own order (`Sensitivity`, `Emitting power`), so this is not a crop that stops short of the row. §22.6 lists "what makes the `Tgc [dB]` row visible" as its sole open question: this crop is a datum for it, and it says the row was absent at 16:28.
4. **The dialog crop disagrees with §23.3 in six of the fifteen fields** (`UI-OVERLAY-05`) - §23.3's driver read of the same dialog in the same mode gives `PRF 600`, `Nb of gates 50`, `Resolution 1.850`, `Velocity scale factor 1.00`, `Emissions/profile 20`, `Tgc [dB] 20`; this crop reads `296`, `726`, `0.123`, `0.49`, `150`, `40`. Eight named cells agree exactly (`US Frequency 4000`, `Burst length 4`, `First gate depth 1`, `Sampling volume 1.776`, `Doppler angle 0`, `Sound speed 1480`, `Number of skipped profiles 0`, channel `1`). The four `89` edits that same table lists are not painted in this crop at all: nothing in it reads `89`, so this pass can neither confirm nor refute them.
5. **...and the same crop disagrees with the column crop of the same session** (`UI-OVERLAY-05 vs UI-SIDEBAR-01`) - Both are channel 1 on 2026-09-18, 16:33 and 16:28; five cells differ (`PRF` 296 vs 600, `Nb of gates` 726 vs 50, `Resolution` 0.123 vs 1.850, `Velocity scale factor` 0.49 vs 1.00, `Emissions/profile` 150 vs 20). Neither value is a transcription error: the dialog crop is arithmetically coherent with itself (`726 x 0.123 = 89.3 mm` against its own `Depth = 90 mm`; `1480 m/s`, `PRF 296 us`, `4 MHz`, factor `0.49` -> ≈153 mm/s against its own `Velocity scale = 154.2 mm/s`), and so is the column crop. They are two different parameter frames, not one frame misread.
6. **`overlay-search-artifacts.png` does not show a `Search artefacts` surface** (`UI-OVERLAY-15`) - The crop carries a small overlay captioned `Sweep PRF` with `Range` (`Fine` / `Medium` ticked / `Large`) and `Sweeping` (`Fast` / `Medium` ticked / `slow`) and buttons `Start`, `Exit`. Nothing in it mentions artefacts. So the `Search artefacts` surface the Tools menu names (UI-MENU-09) has no crop.

The pixels carry all five: `Operating parameters`, `Default parameters`, `Save parameters`, `Recall parameters`, `Tigger parameters` (the app's own spelling of the last). "Caption-less" is a statement about the tree (no button text), not about the screen - and this crop is the oracle the plan says it lacks.
