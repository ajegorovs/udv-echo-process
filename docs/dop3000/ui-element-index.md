# DOP3010 UI element index - the operator's screenshot crops

**What this is.** An indexed, committed-ready record of the hand-cut PNG crops of the live user
interface of the ultrasound scanner application, taken while working the acquisition campaign. The
crops are the only oracle for the application's own button and field captions: the control tree
carries no text for the button classes, so a caption exists on the screen or not at all.

**Who captured it, and when.** The human operator, by hand, on **2026-09-18**, in two passes, between
16:27 and 17:39 as the file mtimes run (the first pass 16:27-16:54, the second 17:24-17:39); values on
screen are the operator's own working values, not patient data, and nothing in the set is confidential.

**Application and mode.** `UDOP DOP3010.43` - the real instrument in **real-experiment mode** (not
the simulation build `UDOP Simul`), channel 1 routed throughout, the recording strip in view
`ready` in the first pass. The mode is carried by the pixels as well as by this sentence: `app-whole.png`
(UI-WINDOW-01) is a whole-window capture whose title bar reads `UDOP DOP3010.43`, beside the
application's own icon. Of the other 40 files it remains true that none contains the title bar.

**The set is PARTIAL.** This is an incomplete pass over the interface, captured in one session, and
it is expected to grow. It is not a screen-by-screen walkthrough: it is a set of regions the
operator chose, so a surface absent here is absent from the *set*, not from the application. Every
gap found is named in the two sections below.

**The `blocking` column** is the *only* field in this index that cannot be read from the pixels:
whether a cursor was captured by an overlay is not a property a crop can show, so every cell states
where its claim comes from. It records the **operator's per-surface answer**, given after walking every
menu of the instrument: `yes (operator's list)` for an overlay the operator classifies blocking, which is
most of them (every `Parameters` entry included); `no (operator's list)` for the small non-blocking set -
`Define TGC`, `Search artefacts` (in both of its states), `Acquire raw data`, and the small cursor info
window that showing cursors spawns; and `unknown (not classified)` for `External Trigger settings`,
which the operator did not classify. It is **not** read from the filenames:
this column was first filled from the operator's own naming convention (a `-blocking` suffix means
blocking), and that convention is now shown to be **unreliable** - the first pass inferred "non-blocking"
for every overlay that left the mouse free, but an Alt-Tab away and back is what freed the mouse, so the
inference was confounded by the very leak the plan records (see `Cross-checks and findings`, finding 13).
Not every crop is an overlay, and those cells say so: `n/a (a dropdown, not an overlay)` for the menu
dropdown crops - the two `Preferences` crops (UI-MENU-03/-04) among them, since an open dropdown is not an
overlay whatever its entries open, and the `Assisted mode` toggle it carries is a button, not an overlay
either - and `n/a (not an overlay)` for the bar, the column, the strip and the whole-window capture.
The question does not arise for a surface that is not an overlay at all.

**How the images were read.** Every one of the 41 files was opened and described from the pixels;
every numeric cell was then re-read from a x5-x6 nearest-neighbour magnification, and the cells that
disagreed between passes were settled by printing the glyph bitmaps and comparing them with the same
frame's own known digits. Three readings were corrected this way in the first pass (see `Cross-checks
and findings`), and the second pass reproduced the worst of the traps on the whole-window capture,
where `PRF [us]` again read `500` from the pixels until the glyph comparison returned `600`. No value
in the table is inferred from the filename.

**Pixel dimensions** are recorded beside each filename. Total: 41 crops, 17 MENU, 20 OVERLAY, 1 SIDEBAR, 1 BAR, 1 STRIP, 1 WINDOW.
The `WINDOW` family is no longer empty: `app-whole.png` (UI-WINDOW-01) is the whole application window.

## Crops

Ids are stable and sortable: `UI-<FAMILY>-<nn>`. Families: `MENU` (the menu bar and its submenus),
`OVERLAY` (overlays and dialogs), `SIDEBAR` (the left parameter column), `BAR` (the bottom/status
strip), `STRIP` (the recording strip), `WINDOW` (the whole application window). Numbering runs the menu
bar left to right, then the dropdowns, then the overlays, then the column, then the bars, then the
window. A crop added after the first pass takes the next free number in its own family and its row sits
in that family's block, so no existing id is renumbered or reused - the operator's rename of
`menu-cursors.png` to `menu-cursors-off.png` therefore keeps UI-MENU-07's id and changes only that
row's `file` cell. The `file` column keeps the operator's own filename unchanged - that name is the
stable key this index is built on.
