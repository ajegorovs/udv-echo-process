# Painted caption recognition — the Channels popup's caption line

**What this is.** `udv_echo_process.acquire.caption_band` reads the one painted line that captions
the `Channels` popup's group box —

```
For the current channel (channel N)
```

— out of a saved popup crop, and returns a **visual attribution**. It is not native text and not an
action authority: every widget in this popup is caption-less (`WM_GETTEXT` returns `""`, ledger
B15), so the line exists as paint or not at all, and a picture of it may never be promoted into
what the application *states*.

**What it is not.** Not OCR: there is no engine, no threshold, no classifier and no nearest-match.
Not an input to a gesture: nothing in the module presses, selects, opens or writes, and no reader of
it may. Not the caller's declaration: the operator's stated channel, a plan's declaration and the
bracketed amounts are absent from its inputs — it reads pixels only.

## When it runs, and only then

`channels-read --capture-dir` produces `CaptureEvidence`. If (and only if) that capture is
`status: ok` — attributed target, foreground, same popup panel, non-blank frames, every amount
bracketed, two frames equal — the two saved frames go to `caption_band.attribute_frames`, which
requires **two** frames and re-derives each frame's pixel digest from its decoded RGB pixels with
the capture path's own `channels_capture.digest` before trusting the digest it was handed. A
supplied digest that does not match the pixels, two frames whose decoded pixels differ, or an
`UNKNOWN` reading on either side is an `UNKNOWN` attribution with a named reason — never a vote.
Anything less leaves `capture.visual_caption` `None`. A single grab never yields an attribution,
because it cannot be checked against itself. Equal, independently verified pixel digests make the
two readings identical by construction, so the old "the frames read different captions" branch is
superseded by the pixel comparison.

`band_digest` stays the recognised band's own identity and is never conflated with a frame's
pixel digest, the file digest, or the template digests.

The report keeps two different fields on purpose: `capture.caption` stays `UNKNOWN`
(`recognition: NOT_PERFORMED`) because no native text exists, while `capture.visual_caption`
carries the pixels' reading with `native_fact: false` and `action_authority: false`.
`per_channel.channel` stays `UNKNOWN` and no amount is touched — the picture never overwrites a
native field, and no writer's authority is widened by this reader.

## The measured signature (a verification constant, never a search)

| fact | value |
|---|---|
| popup crop size | `393x426` |
| ink | pure white on flat `(64,72,112)`; exactly two colours in the band |
| caption ink block | rows `263-275` inclusive (parentheses descend to 275) |
| caption left edge | `x = 88` |
| group-box top rule | rows `281-282`, reaching `x = 382` |
| separator rule above | the nearest long rule above the group box (bounds the band) |
| digit cells | first ink at `x = 279`, pitch `7 px`, at most 2 digits |
| supported glyphs | `{0,1,2}` learned from measured captures; closing `)` at `-1 px` of the next cell |
| supported channels | `{1, 2, 10}` — the only caption lines ever photographed |

A crop that does not sit exactly on this signature is `UNKNOWN` with the check that failed named.
The glyph set and the channel set are deliberately different facts: `0`, `1` and `2` are real
rasters (they spell `10`), but a band whose learned glyphs compose `0`, `11`, `12`, `20`, `21` or
`22` is `UNKNOWN`, because those channels were never photographed. Digits `3`-`9`, three-digit
captions, another font, another DPI/theme and another popup size are **outside support** and refuse
rather than extrapolate.

A **saved** frame is size-checked from the PNG header before `load()`, `convert()` or any array
allocation; the measured popup `393x426` is the pixel cap, and no second arbitrary bound exists. A
host without the `acquire` extra (no Pillow) gets a typed `UNKNOWN` naming the missing extra, not
an `ImportError`. A recognised report's diagnostics state the band's **actual tight width**, not
the width of the fixed right-window slice it was matched inside.

## The templates and their provenance

Committed rasters live in `acquire/caption_band_templates.py`, generated by
`caption_band.build_templates` from the fixtures in `tests/data/caption-band/` (see that
directory's `README.md` for the captures, roles and digests). Each raster records its source
capture **id** and that file's SHA-256, never a path, handle or machine identity.
`tests/test_acquire_caption_band.py` re-learns the whole set from the committed PNGs and fails if
the package data and the fixtures disagree, so the oracle cannot drift into hand-written data.

Re-derive after adding measured captures (this is the only supported way to widen the alphabet):

```bash
uv run --extra acquire python - <<'PY'
from pathlib import Path
from udv_echo_process.acquire.caption_band import build_templates
set_ = build_templates({"train-channel-1": (Path("tests/data/caption-band/train-channel-1.png"), "1")})
print([(g, t.rows) for g, t in set_.digits.items()])
PY
```

Widening the alphabet needs **new measured captures of those channels** (a `3`-`9` photograph, not
an extrapolation from `1`, `2` and `10`).

## Evidence level, and coverage limits

- **live** (one pass, 2026-10-21) — `channels-read --capture-dir … --json` against the
  operator-opened popup returned `capture.visual_caption.status: RECOGNIZED`,
  `channel: 1`, `frames_agreed: true`, while `capture.caption` and `per_channel.channel` stayed
  `UNKNOWN` and nothing was pressed. The dispatch record is the local agent artifact
  `.hermes/scratch/multiplexer-development/caption-recognition-live.log` (git-ignored, not part of
  the repository); the popup rect it read was `393x426`;
- **replay-verified** — everything else: the four retained crops (channel 1, channel 2, channel
  10, and the return to channel 1) and the two-frame rule, through the same `channels-read
  --capture-dir` path and the CLI, in `tests/test_acquire_caption_band.py`. Both frames of every
  fixture pair are byte-identical, so replay proves stability, not atomic stillness;
- **measured** — every geometry constant above and the glyph rasters came from those retained
  captures;
- **unknown / not covered** — channels `2` and `10` have not been seen live through this reader
  (only their saved crops); digits `3`-`9`; composed channels `0`, `11`, `12`, `20`, `21`, `22`;
  three-digit captions; other DPI, theme, font or popup size; display scaling other than the one
  the capture path already refuses; and any statement about mode, ticks, amounts or configuration.
  The live pass covers one channel in one sitting.
